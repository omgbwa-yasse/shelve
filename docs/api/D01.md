## Règles métier relevées dans les contrôleurs et vues

1. **Référentiels globaux.** Aucune table du domaine (sauf `settings`) ne porte
   `organisation_id`. Le contrôle d'accès doit donc **permettre** l'accès à tous les
   agents authentifiés : `PolicyService::access-in-organisation` a été corrigé en ce
   sens (avant le portage, le fallback renvoyait `false` pour tout modèle sans
   organisation → 404 systématique sur les référentiels). Une relation
   `organisations()` en many-to-many (ex. `Activity`) est une **affectation**, pas une
   propriété : elle ne restreint pas l'accès.
2. **`settings` est org-scopé.** C'est la seule table du domaine avec
   `organisation_id` : l'index applique `scopeForUserAndOrganisation` (global ∨ mon
   org ∨ moi). Une ligne sans organisation (`organisation_id NULL`) est globale et
   lisible par tous.
3. **Contact principal unique.** Un contact externe marqué `is_primary_contact`
   retire ce statut aux autres contacts de la même organisation externe (store ET
   update).
4. **Suppression gardée.** Un contact/organisation externe lié à des courriers ne se
   supprime pas (409 en API). Une organisation dissocie d'abord ses contacts.
   Un mot-clé utilisé par des notices ne se supprime pas (409). Une catégorie de
   paramètres qui contient des paramètres ne se supprime pas (409). Une liste de
   référence utilisée par des définitions de métadonnées ne se supprime pas (409).
5. **Référence circulaire.** Changer le parent d'une catégorie de paramètres est
   refusé (422) si cela crée un cycle.
6. **Listes de référence** : `code` unique dans la liste, `created_by`/`updated_by`
   toujours posés depuis l'agent authentifié (jamais acceptés du client).

## Découvertes / écarts corrigés

| Découverte | Traitement |
|---|---|
| **`Setting::setValue` (Blade) créait un doublon** violant `unique:settings,name` | L'API écrit sur la ligne du paramètre (`value` mis à jour) au lieu de cloner ; `resetValue` efface `value`. Documenté en commentaire. `SettingMergedStructureTest` (test préexistant) échoue pour la même raison — preuve que la sémantique « instance personnalisée » est incompatible avec le schéma actuel. |
| **Autorisation inexistante côté Blade** pour `KeywordController`, `LawArticle`, `Sort`, `Communicability`, `AuthorContact`, `External*`, `ReferenceList` (risque R04) | Policies créées et branchées (`{ressource}_{viewAny,view,create,update,delete}`), permissions ajoutées au `PermissionSeeder`. La politique RBAC (quels rôles reçoivent quoi) reste à décider par le propriétaire du domaine — aucun rôle ne se voit octroyer ces permissions par le seeder. |
| **`PolicyService::hasPermission` par Gate dynamique** ne voyait pas les permissions créées après le boot | `BasePolicy::hasPermission` interroge désormais `User::hasPermission()` (tables natives) — équivalent pour l'existant, correct pour les permissions tardives. |
| `author_types.description` NOT NULL sans défaut | Fourni systématiquement (tests). |
| `reference_values.created_by` NOT NULL sans défaut | Posé depuis l'agent authentifié. |
| `Law::$fillable` omettait `law_type_id` (NOT NULL) | Ajouté lors du portage. |
| `Language::switch` est une notion de session, sans équivalent stateless | Exposé comme validation de locale (`/languages/{locale}/activate`) ; la localisation réelle passe par `Accept-Language` (CONVENTIONS §1.0.3). |

## Validation

Toutes les règles des contrôleurs Blade ont été reportées à l'identique dans les
`Store/Update` requests, **y compris les 73 constructions dynamiques de 1.0.2**
(uniqité `ignore($this->route(...))`, `prepareForValidation` pour le `trim` des
mots-clés). Aucune règle métier n'a été perdue (R01).

## Autorisation (R04)

- Policies créées : `AuthorContactPolicy`, `ExternalContactPolicy`,
  `ExternalOrganizationPolicy`, `ReferenceListPolicy`, `ReferenceValuePolicy`.
- `ReferenceValuePolicy` et `LawArticlePolicy` réutilisent les permissions de leur
  parent (`reference_list_*`, `law_*`) : une valeur ou un article n'a pas de sens
  hors de son contenant.
- 1 test par règle d'autorisation : 401 sans token, 403 sans permission, refus 404
  sur l'inconnu.

## Isolation multi-organisation (R03)

- Référentiels globaux : test « partage entre organisations » (un agent d'une autre
  organisation lit les mêmes données — aucune restriction silencieuse).
- `settings` org-scopé : test que les paramètres d'une autre organisation ne sont
  pas visibles à l'index.

## Tests et conformité

- **157 tests Feature** (`tests/Feature/Api/V1/`) — tous verts : CRUD, validation,
  filtres/tri, autorisation, actions métier, sous-ressources, isolation.
- **Suite de conformité** `contracts/conformance/D01/referentials.test.js` — 15 tests,
  verte contre l'API réelle, rejouable telle quelle contre Spring Boot.
- La suite complète passe de **227 à 125 échecs préexistants** grâce à la correction
  de `access-in-organisation` et de `hasPermission` — sans introduire de régression.
