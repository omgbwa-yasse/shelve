# D03 — Localisation physique (analyse de portage)

> Note d'analyse du portage en API v1 — étape 1.2, première vague.
> Source : contrôleurs Blade, vues associées, schéma MySQL, inventaire 1.0.1.

## Périmètre

7 familles de contrôleurs Blade, **46 routes « à porter »** sur 64 (les 18 autres sont
des vues `create`/`edit` abandonnées). **0 action métier** : tout est CRUD.

| Contrôleur Blade | Ressource API v1 | Portée org | Type |
|---|---|---|---|
| `BuildingController` (+ routes `trolleys`) | `buildings` | globale | CRUD |
| `FloorController` | `floors` | globale | CRUD |
| `RoomController` | `rooms` | **org-scopée** (`organisation_room`) | CRUD |
| `ShelfController` | `shelves` | **org-scopée** (via salle) | CRUD |
| `ContainerController` | `containers` | **org-scopée** (via rayonnage + `creator_organisation_id`) | CRUD |
| `ContainerPropertyController` | `container-properties` | globale | CRUD |
| `ContainerStatusController` (+ routes `access`) | `container-statuses` | globale | CRUD |

**Fusions** : les routes `trolleys` (`BuildingController`) et `access`
(`ContainerStatusController`) sont des alias du même contrôleur → fusionnées dans la
ressource canonique.

## Règles métier relevées

1. **Portée organisation (R03)** — c'est le point structurant du domaine, et le
   premier du plan où l'isolation est réelle (D01 était global) :
   - `rooms` : portées par la pivot `organisation_room` (l'index Blade filtre par
     `whereHas('organisations')`, `destroy` vérifie l'appartenance).
   - `shelves` : héritent de l'organisation de leur salle.
   - `containers` : héritent de leur rayonnage/salle, et portent en plus
     `creator_organisation_id`.
   - `buildings`, `floors`, `container_properties`, `container_statuses` : **globaux**,
     aucun filtrage dans l'index Blade.
2. **Isolation en 404, pas en 403** (CONVENTIONS §4) : toute ressource hors de
   l'organisation courante répond 404 sur show/update/destroy — résolu par une portée
   `inOrganisation()` sur les modèles (`Room`, `Shelf`, `Container`), appliquée aussi
   à la résolution des routes. Test bloquant par ressource (R03).
3. **Création bornée au périmètre** : une salle est rattachée à l'organisation de
   l'agent ; un rayonnage doit être posé dans une salle de l'organisation (422 sinon) ;
   un conteneur sur un rayonnage de l'organisation (422 sinon).
4. **`creator_id` / `creator_organisation_id` jamais acceptés du client** : toujours
   posés depuis l'agent authentifié. Le Blade utilisait un `creator_id => 1` codé en
   dur pour les bâtiments — corrigé.
5. **Champs calculés** (ruban b — calculés par les index/show Blade, répliqués dans
   les Resources) : `shelves_count`, `is_visible`, `effective_visibility` (héritage de
   la visibilité du bâtiment) sur les salles ; `total_capacity`, `occupied_spots`,
   `available_spots`, `occupancy_percentage`, `volumetry_ml` sur les rayonnages
   (`withCount('containers')` à l'index pour éviter le N+1).

## Validation

Règles des contrôleurs Blade reportées à l'identique : `visibility in:public,private,inherit`,
`type in:archives,producer`, unicités (`containers.code`, `container_properties.name`,
`container_statuses.name` avec `ignore($this->route(...))`), `face/ear/shelf` en
`numeric|max:10`. Les `Update*Request` sont en `sometimes` (PATCH partiel).

## Autorisation (R04)

Policies existantes branchées : `BuildingPolicy`, `FloorPolicy`, `RoomPolicy`,
`ShelfPolicy`, `ContainerPolicy`. Deux absentes créées : `ContainerPropertyPolicy`,
`ContainerStatusPolicy`. Permissions ajoutées au `PermissionSeeder`
(`building_*`, `floor_*`, `room_*`, `shelf_*`, `container_*`, `container_property_*`,
`container_status_*`). Test 401/403 par ressource.

## Découvertes

| Découverte | Traitement |
|---|---|
| **`trolleys` et `access`** sont des alias de `BuildingController` / `ContainerStatusController` | Fusionnés dans `buildings` / `container-statuses` — 12 routes d'inventaire couvertes par 2 ressources |
| **Isolation org absente des Policies** (`Room`/`Shelf`/`Container` n'ont pas de colonne `organisation_id` → le Gate `access-in-organisation` les laissait passer) | Portées `inOrganisation()` sur les modèles, appliquées à l'index ET à la résolution des routes (404) — la garantie d'isolation est portée par les modèles, comme le feront les filtres Hibernate en phase 3 |
| `rooms.code` est `varchar(10)` — toute valeur au-delà est rejetée par MySQL | Tests adaptés (codes courts) |
